# نموذج الأمان
## ما هو منفذ حاليًا
- allowlist من 52 ملفًا ببصمات Git/SHA-256؛ لا نقل لتاريخ المصدر أو أندرويد أو أسرار.
- فحص تبعيات وlockfile، والتحقق من ملفات offline قبل بناء Artifact.
- بداية Artifact مغلقة؛ لا تشغيل خدمة staging ولا نشر عام. CI بلا صلاحيات نشر.
هذا ليس تفعيل ويب مكتملًا، ولا قبولًا أمنيًا للمنتج.

## الحدود والهدف
- صلاحيات السيرفر مستقلة: عميل، إدارة metadata، مالك إدارة، ومخول محتوى نسخ. موظف الدعم لا يحصل على بيانات المحل.
- أي tenant ID من العميل يجب ربطه بـsession وصلاحيات مخزنة؛ لا معرفة ID كافية للتنزيل.
- تسجيل الحساب لا يمنح اشتراكًا مدفوعًا. لا default admin/password؛ bootstrap محلي تفاعلي وMFA واسترداد مضبوط.
- كلمات مرور مشتقة بـخوارزمية maintained؛ brute-force limits على الدخول/التفعيل/الاستعادة، لا raw credentials في logs أو URLs.
- nonce مرتبط بجلسة وحساب وغرض وتثبيت؛ expiry واستهلاك ذري، واختبارات سباق/replay.
- التفعيل الأول وتخصيص الكاتب/سلطة الرفع معاملات SQLite بقيود uniqueness، لا ملفات JSON مشتركة.
- مفاتيح توقيع خارج Git/public/Service Worker، مع kid ودوران يحفظ التصاريح المعتمدة خلال الانتقال.
- XSS/HTML escaping/CSP، CSRF، CORS محدود، cookies آمنة، حدود أحجام ومعدلات واستعلامات؛ لا تجميد بيانات عميل بسبب خطأ UI فقط.
- المعدل والحضور إشارات تشغيل/أمن، ليست إثبات عتاد. القديم يستطيع إثبات وجوده دون حصوله على upload grant.
- الأوفلاين قد يستمر حتى نهاية تصريح موقع سابق بعد الحظر؛ تغيير كلمة المرور/session لا يبطل تصريحًا أوفلاين سحريًا.
- تعديل JS ومسح التخزين وتغيير الساعة لا تمنع نهائيًا. لا IMEI ولا tracking fingerprint خفي.
- لا uploads دون استحقاق منفصل وموافقة؛ لا رفع تقارير لاستخراجها مرة أخرى.
- public repository لا يصلح مكانًا لأسرار/بيانات أعمال. نوصي بجعله خاصًا، ولا نغيره دون موافقة.
